## Picked (and why)
Pinned the image-conversion catch in `validateFiles`. The path: a dropped file
whose first bytes match a PNG/JPG magic header (so `detectImageMime` routes it to
the converter) but whose body is not a real image, so pdf-lib's `embedPng` throws.
`validateFiles` wraps that in `try/catch` and pushes a per-file error rather than
letting the rejection escape the loop. That boundary was genuinely uncovered: the
existing "gibberish .pdf" test has no image magic and hits the final fallthrough
(line 97), not the catch; and `image-import.test.ts` exercises `embedPng`'s
rejection directly but not the validate.ts wrapping that *isolates* the failure to
one file. The dangerous regression — removing the catch — would turn a single
corrupt image into an unhandled rejection that takes down the whole drop, including
good files dropped alongside it. Two tests pin it: one asserts the per-file error
message, one asserts a good PDF in the same batch still validates (the `continue`
isolation). Pure additive — no source change.
