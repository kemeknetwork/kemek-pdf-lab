## Picked (and why)
The `MAX_DIM_PT` (2000pt) downscale clamp in `imageBytesToPdf` was the one
real-logic branch across validate/image-import/operator that nothing exercised.
Every existing image test uses a 1×1 fixture, and the test file's own comments
explicitly acknowledge "well under MAX_DIM_PT" — i.e. the `longer > MAX_DIM_PT`
branch (and the aspect-ratio-preserving scale) was *never taken*. The source
documents exactly why it matters: "A 4032×3024 phone photo at 72 DPI is 56×42
inches; without a cap we'd produce absurd page sizes." A regression there —
inverting the comparison, dropping aspect ratio, or scaling a single axis —
would silently emit a 56-inch page for a routine photo import and slip past the
entire current suite. That clears the bar; it is not coverage-padding (it pins
an untouched branch with a concrete user-facing failure mode), and it is a
fresh file vs. last cycle.

The fixture problem: PNG won't work (pdf-lib fully decodes PNG, so a spoofed
IHDR fails). pdf-lib's `JpegEmbedder`, however, reads dimensions straight from
the SOF0 marker and never decodes the entropy-coded scan data — so patching the
1×1 JPEG fixture's SOF0 height/width fields makes `embedJpg` report any size we
declare. The helper locates SOF0 (`0xFF 0xC0`) and rewrites the 4 dimension
bytes; three tests pin landscape clamp, portrait clamp, and the exact-boundary
(`=== MAX_DIM_PT` stays unscaled because the guard is strictly `>`).
